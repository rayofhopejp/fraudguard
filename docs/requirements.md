# FraudGuard 要件定義 v2

> v1(初版)からの主な変更点は冒頭の「改訂履歴」を参照。本文中、v1から変更・追加した箇所には `[v2]` を付記している。

## 改訂履歴(v1 → v2)

以下のレビュー指摘を反映した。

1. **[重大]** 「監視の無効化」への対策が要件に無かったため、35章(監視継続性・自己監視)を新設。詐欺犯が被害者に監視アプリの無効化・削除を指示するケースは本システムの脅威モデルの中核であり、Phase 1相当の優先度とした。
2. **[重大]** 遠隔切断コマンドの配信がFCM一本足だったため、23章にポーリングAPIを追加(Doze/OEM制限でFCMが届かないケースの保険)。
3. **[重大]** ブラックリストの「効果」が未定義だったため、18章に定義を追加。
4. コマンド署名の鍵管理方式を、8.1章で非対称鍵方式(サーバー署名・端末検証)に具体化。
5. 4.3章で、通話「監視」と「遠隔切断」に必要な権限を分離し、ROLE_DIALER化(デフォルト電話アプリ化)を独立したフェーズとして扱うよう変更。監視のみならROLE_DIALER不要。
6. Push通知本文へのセンシティブ情報埋め込みを避けるよう16.3・17章を更新。
7. オンボーディング/ペアリングフローが未記載だったため34章を新設。
8. 26章に同意取得の記録(監査ログ化)を追加。
9. 27章(通話録音)の実現可能性に関する注記を強化。
10. **36章(インフラ構成)を新設。バックエンドはAWSを前提とし、個人・家族規模でのコスト試算を明記。**

## 1. 目的

Android端末上で、特殊詐欺・投資詐欺・遠隔操作詐欺・メッセージアプリ経由の詐欺などの兆候を監視し、家族へリアルタイムに通知する。

対象は自分・家族の同意済み端末へのサイドロード運用を想定する。Google Playでの一般配布は前提としない。

主な目的は以下。

- 不審な電話の早期検知
- 海外番号や異常な電話番号の検知
- 長時間の不審通話の検知
- 不審な発信の検知
- 大量の海外着信の検知
- SMS内容の家族通知
- LINE / Telegram / Signal等を使った詐欺兆候の検知
- 新規アプリインストールの監視
- 遠隔操作アプリ導入の高優先度警告
- 家族による遠隔通話切断
- **[v2] 監視機能自体が無効化・停止された場合の家族への通知**
- 将来的な通話録音・文字起こし・詐欺文脈判定

## 4. 通常電話監視

### 4.1 取得する情報

(v1と同様。省略せず以下に記載)

着信・発信ごとに以下を取得・記録する。

- 一意な通話ID
- 監視端末ID
- 電話番号
- 着信 / 発信
- 着信時刻
- 発信時刻
- 通話開始時刻
- 通話終了時刻
- 通話時間
- 現在の通話状態
- ホワイトリスト登録有無
- 国内 / 海外
- 番号形式の正常 / 異常
- リスクレベル
- リスク判定理由

### 4.2 通話状態

最低限以下を扱う。

- 着信中
- 発信中
- 通話中
- 保留
- 終了

通話がACTIVEになった時点から通話時間をリアルタイム計測する。

### 4.3 権限方式の段階分け `[v2]`

通話「監視」(着信/発信/通話時間の取得、7章の警告ルール)と、「遠隔切断」(8章)は必要な権限レベルが異なるため、以下のように分離する。

| 機能 | 必要な権限 | ROLE_DIALER要否 |
|---|---|---|
| 着信/発信/通話時間の監視 | `READ_PHONE_STATE` + `TelephonyCallback`(`READ_CALL_LOG`) | 不要 |
| 遠隔通話切断(`Call.disconnect()`) | `InCallService` として通話制御権を持つ | 実質的に必要(デフォルト電話アプリ化) |

**理由:** ROLE_DIALER化は、既存の電話アプリ(発信・着信履歴・連絡先UI等)を丸ごと自作・置換することを意味し、実装コストと高齢ユーザーの混乱リスクが大きい。Phase 1の前半では監視機能のみを軽量権限で提供し、遠隔切断機能を追加するタイミングでROLE_DIALER化に踏み込む、という2段階リリースを推奨する。

## 5. 電話番号判定

(v1と同様)

### 5.1 国内番号

日本の番号として正規化して判定する。可能であればE.164形式へ統一する。

例: `09012345678` / `090-1234-5678` / `+819012345678` を同一番号として扱えるようにする。

### 5.2 海外番号

日本の `+81` 以外の国番号を原則として海外番号扱いする。海外番号からの着信・海外番号への発信は、ホワイトリスト未登録の場合に警告対象とする。

### 5.3 異常・存在しない形式の番号

以下を警告対象とする。

- 桁数が明らかに不正
- 電話番号として解析不能
- 存在しない国番号
- E.164として不正
- その他明らかな異常形式

「その番号が実際に契約・割当されているか」の確認はAndroid単体では必須要件としない。将来的に外部番号データベースを利用可能な構造にする。番号解析にはlibphonenumber等の利用を推奨。

## 6. ホワイトリスト

### 6.1 基本機能

電話番号ごとに以下を管理する: 電話番号 / 表示名 / 有効・無効 / 備考 / 作成者 / 作成日時 / 更新日時。

### 6.2 同期

ホワイトリストはサーバー側を正とし、監視端末へ同期する。監視端末側にはオフライン時でも判定できるローカルキャッシュを持つ。家族アプリからホワイトリスト追加・編集を可能にする。

---

## 7. 電話の警告ルール

(7.1〜7.6はv1と同様のため要点のみ記載)

- 7.1 海外番号から着信 → WARNING/HIGH
- 7.2 海外番号へ発信 → CRITICAL候補
- 7.3 ホワイトリスト外国内番号へ発信 → WARNING
- 7.4 [v3] ホワイトリスト外の相手との通話が続いたら段階的に警告する。**1分・3分・5分・10分・15分、以降は15分おきに通話が終わるまで**。説得が長引くほど危険度が上がるため、一度警告して終わりにしない
  - LINE等のアプリ内通話(10.3章)では**1分の通知を出さない**。相手を電話番号で識別できず、家族との日常的な短い通話まで拾ってしまうため。それ以外の刻みは通常の電話と同じ
  - どの経過時間で知らせるかを決めるのは端末側。サーバー側の判定は最短(1分)に合わせた下限を持つだけで、それ未満の通話時間が届いた場合の保険にすぎない
- 7.5 海外番号から10分以内に3件以上着信 → CRITICAL
- 7.6 不正形式番号 → WARNING

## 8. 遠隔通話切断

通信フロー: `Family App -> Server -> FCM Data Message -> Monitor App -> Call.disconnect()`

### 8.1 安全要件 `[v2: 鍵管理方式を具体化]`

遠隔切断は無条件に実行しない。最低限以下を検証する。

- deviceId / commandId / callId / コマンド種別 / 発行時刻 / 有効期限 / nonce
- 署名(推奨方式は下記)
- 対象通話が現在ACTIVEであること
- 対象通話IDが一致すること
- 同一コマンドを二重実行しないこと(20.1のローカルDBに使用済みcommandIdを保持)

**署名方式(推奨): 非対称鍵**

- サーバーがコマンドごとに秘密鍵(Ed25519等)で署名する
- 監視端末はペアリング時にサーバーの公開鍵を受け取り、コマンド検証に使う
- 対称鍵(HMAC共有シークレット)方式は、端末側に漏洩した場合に他端末へのなりすましリスクがあるため避ける
- 端末紛失時は該当端末のペアリングを無効化するだけで、他端末の鍵には影響しない

**[v2] 配信経路の冗長化**

FCM Data Messageのみに依存すると、Doze/OEMのバックグラウンド制限で遅延・未達となる可能性があるため、Monitor側は定期的に `GET /devices/{id}/commands/pending`(23章参照)をポーリングし、FCM未達時のフォールバックとする。緊急性の高い遠隔切断ではこの冗長化が重要。

### 8.2 監査ログ

以下を保存する: 誰が切断を要求したか / いつ要求したか / 対象端末 / 対象通話 / 実行結果 / 成功・失敗理由。

## 10. LINE / Telegram / Signal 等の監視

### 10.1 他アプリ内部DBの直接取得は前提としない

LINE / Telegram / Signalの内部データベースや正式な通話履歴を直接読み取ることは必須要件としない。

### 10.2 NotificationListenerServiceによる監視

対象アプリの通知を監視する(通知元アプリ / タイトル / 本文 / 時刻等)。対象候補: LINE / Telegram / Signal / WhatsApp / その他。

### 10.3 LINE通話兆候

通知内容から着信・通話開始・通話中・終了等を推定する。確実性は低いため、イベントには信頼度(confidence)を持たせる。

#### [v3] 通話以外の通知をどこまで報告するか

**対象アプリの通知をすべて報告することはしない。** メッセージングアプリの通知は一日中発生し、その大半は詐欺と無関係な私的な会話である。全部を家族へ送るのは監視として行き過ぎであり、30章が避けよと定めるアラート疲れも確実にまねく。報告するのは次の2つに限る。

| 条件 | 本文 | 信頼度 | 位置づけ |
|---|---|---|---|
| 本文に詐欺でよく使われる語句(9.1章と同じ語彙)を含む | **添える** | 0.65〜0.95(一致語数による) | 家族が判断するには本文が要る(16.3章[v3]と同じ判断) |
| 直近24時間以内にインストールされたアプリからの通知 | **添えない** | 0.3 | 14.2章の「導入 → 起動 → 通知発生」を成立させるための観測 |

どちらにも当たらない通知は**イベント自体を作らない**。中身をサーバーへ送らないだけでなく、通知があったという記録も残さない。

本文の無い観測は単体では警告に上げず(INFO)、14.2章の相関判定の材料としてのみ意味を持つ。同じ通知が編集・既読で何度も更新されるため、端末側で内容の指紋を持って重複報告を抑える(指紋のみを保持し、内容そのものは端末にも残さない)。

#### [v3] 通話そのものを直接検知する

以下はすべて実機(Pixel 7 Pro / Android 16, LINE)で計測して確定した挙動。

**Telecom経由だけでは足りない。** LINEは通話を自己管理型(SelfManaged)のPhoneAccountとして登録しており、既定ではデフォルト電話アプリのInCallServiceへ通知されない。Monitor側で `INCLUDE_SELF_MANAGED_CALLS` を宣言すれば通知されるようになるが、**LINEは通話開始から4〜7秒でTelecomから通話を取り下げる**(通話自体は続いている。Telecomの記録上も`endTime`がそこで打たれる)。したがってTelecom経由で得られるのは**通話開始の検知だけ**で、通話時間の計測も遠隔切断もできない。実際、コマンド発行の2秒後にInCallServiceがアンバインドされ、ポーリングが一度も回らなかった。

**通話中通知が実体に最も近い。** LINEはAOSP標準の `Notification.CallStyle` で通話中の常駐通知を出し、これは通話が終わるまで残る。この通知から次が得られる。

| 得たいもの | 手段 |
|---|---|
| 通話開始の検知 | 通知の出現(Telecom経由でも可) |
| 通話開始時刻・通話時間 | `Notification.when` |
| 通話終了の検知 | 通知の消滅 |
| **遠隔切断** | `Notification.EXTRA_HANG_UP_INTENT` のPendingIntentを`send()` |

切断用PendingIntentは発行元(LINE)の権限で実行されるため、こちらに追加の権限は要らない(通知アクセスのみ)。CallStyleはプラットフォームの規約なので、LINEのUI構造に依存せず、CallStyleを使う他のアプリにもそのまま通用する。**実機でLINE通話の遠隔切断に成功している。**

なお「アプリのプロセスを終了させて通話を切る」は成立しない。通話中のLINEはフォアグラウンドサービスを持つため、shell権限の `am kill` でも落ちない(実機で確認)。`killBackgroundProcesses()` はAndroid 14以降そもそも自プロセスしか対象にできない。

実装上の注意:
- 通話UIはアプリ側の責務なので、こちらのUIは出さないこと(LINEの通話画面を覆って通話の妨害になる)。
- 通話中はコマンドのポーリングを**通知監視側で**回すこと。Telecomは数秒で手を引くため、InCallService側のポーリングは当てにできない。
- Telecomと通知の双方が同じ通話を検知するため、通知側はTelecomが採番したcallIdを引き継いでイベントの二重報告を避ける。引き継ぎには期限を設けること(無期限だと次の通話が前回のcallIdを名乗り、誤った通話を切る危険がある)。

アプリ内通話には電話番号が無く、6章のホワイトリスト(番号単位)が使えない。相手が誰かは原理的に分からない。

- **既定では通知する。** 詐欺の側がLINEへ誘導してくるのが実際の手口であり、相手が分からないことを理由に黙るのは、最も知らせるべき通話を見逃すことになる。
- **家族が「これは家族の通話」とマークしたら、その通話については以降通知しない。** 番号を持たない通話に対する、ホワイトリストの代わりの抑制手段。マークは通話単位で、他の通話や他の端末には及ばない。
- マーク後もイベント自体は記録し、14章の相関判定の対象からは外さない。

マークの導線はSlack通知に載せるリンク。Incoming Webhookではボタン(Interactivity)が使えず、Family WebはCognito前提のため、署名付きトークンを含むリンク自体を認証情報とする。リンクを持つ者にできるのはその通話1件の通知を止めることだけで、監視の停止や設定変更はできない。GETは確認画面のみを返し、状態を変えるのはPOSTだけとする(Slackがリンクプレビューのために自動でGETするため、GETでマークすると投稿した瞬間に自分でマークが付く)。

## 11. 新規アプリインストール監視

端末に新しいアプリがインストールされた場合、原則としてすべて家族へ通知する。取得情報: アプリ名 / パッケージ名 / インストール時刻 / 監視端末ID / インストール元(取得可能なら) / リスクカテゴリ / リスクレベル / 判定理由。アプリアップデートは原則として新規インストール扱いしない。

---

## 12. 新規アプリのリスク分類

- 12.1 通常通知(一般ゲーム・天気・ショッピング等): INFO/NORMAL
- 12.2 メッセージング系(Telegram/Signal/WhatsApp): WARNING
- 12.3 遠隔操作系(AnyDesk/TeamViewer/RustDesk/AirDroid等): CRITICAL。将来的にパッケージ名固定リストだけでなくカテゴリ・署名・アプリ情報でも判定可能にする。

## 13. 新規アプリ初回起動

インストールから数分以内の初回起動 / 通話中の新規アプリ起動 / 遠隔操作アプリの直後起動 / Telegram・Signal等の直後起動、を特に重要視する。

**[v3] 実機検証で判明した制約 — 初回起動検知はリアルタイムに使えない。**
他アプリの起動を知る手段は `UsageStatsManager` しかないが、使用状況の履歴はシステムが定期的にまとめて書き出す方式で、起動直後の問い合わせでは取得できない(実機では通話中のインストール直後に何度問い合わせても0件だった)。
したがって本章の検知は **事後の裏付け情報** と位置づけ、通話中にリアルタイムで介入する判定材料にはしない。14.1章の遠隔操作詐欺の判定は起動を待たず、**通話中のインストール検知のみで成立**させる。

実装上さらに次の2点に注意する(いずれも実機で発覚):
- 問い合わせ範囲は毎回「監視窓の全体」を見る。「前回チェック以降」にすると、遅れて書き出されたイベントは範囲が過ぎた後に現れるため永久に取りこぼす。報告済みは監視対象から外すので重複はしない。
- 問い合わせの終端は現在時刻より先に取る。端末の時計が一度でも進んでいると使用状況の集計バケットの開始時刻が未来になり、現在時刻を終端にすると丸ごと範囲外になる。

## 14. リスク相関判定

**[v3] 14.1章の成立条件:** 「未登録番号との通話」+「遠隔操作アプリのインストール」で CRITICAL とする(13章[v3]の制約による)。初回起動が確認できた場合は通知の文面を強める。

## 16. 家族Push通知

Firebase Cloud Messaging等を使用する。

- 16.1 1台の監視端末に複数家族を登録可能
- 16.2 1家族ユーザーが複数のPush端末を保持可能
- 16.3 通知権限は家族ごとに設定可能(受け取る最低リスクレベル / 遠隔切断可否 / ホワイトリスト編集可否 / 閲覧のみ)

**[v3] 通知本文に含める情報(v2から方針変更)**

v2では「ロック画面からの覗き見を避けるため、通知には電話番号・SMS本文を含めない」としていたが、実運用の検討により**家族向けSlack通知には相手番号・SMS本文・判定理由を含める**方針へ変更した。

理由: 家族は本文を読まなければ詐欺かどうかを判断できず、「警告が来たので詳細を見にアプリを開く」という一手間が、緊急時(通話中に切断すべきか判断する場面など)の対応を遅らせる。通知先が家族内の非公開Slackチャンネルであることを前提に、覗き見リスクよりも判断の速さを優先する。

ただし以下は維持する。

- Webhook URL自体は認証情報として扱い、ログ・ソース・リポジトリに残さない(25章)
- SMS本文は通知内では長さを制限し、全文はFamily Web(認証必須)で確認する
- サーバーログには本文・電話番号を出力しない(25章)

この判断は通知先がSlackであることに依存する。将来FCMでスマートフォンのロック画面へ直接通知する場合は、その経路については改めてv2の内容最小化方針を適用するか検討すること。

## 34. オンボーディング/ペアリングフロー `[v2 新設]`

監視端末を家族アカウントに紐付ける手順を以下の通り定義する。

1. 家族側(FraudGuard Family)で監視対象端末を新規登録し、ペアリングコード(短期間有効なワンタイムコードまたはQRコード)を発行する
2. 監視対象端末側でMonitorアプリを起動し、ペアリングコードを入力/QRスキャンする
3. Monitorアプリは初回同意フロー(26章参照)を表示し、同意内容を記録した上でサーバーに登録要求を送る
4. サーバーは該当端末の公開鍵ペア(8.1の署名検証用)を生成・払い出し、`device_pairings` に記録する
5. 登録完了後、監視端末は必要な権限(通知アクセス、電話関連権限等)の許可を順にガイドする
6. 家族ユーザーはペアリング完了後、監視対象端末への閲覧・通知権限が自動的に付与される(登録した家族が「管理者」ロールを持つ)

**端末の無効化(紛失・監視終了時):** 家族アプリから対象端末のペアリングを無効化すると、`device_pairings` の当該レコードが失効し、以後そのAPIキー/署名検証は全て拒否される。

## 35. 監視継続性・自己監視(ハートビート) `[v2 新設]`

### 35.1 目的

本システムの脅威モデルでは、詐欺犯が被害者に対し「このアプリは怪しいから消して」「通知の許可を切って」等の指示を出すケースが強く想定される。監視が静かに止まっていること自体を検知できなければ、システム全体の前提が崩れる。そのため、監視の生存確認を独立した要件として扱う。

### 35.2 ハートビート

- Monitorアプリは一定間隔(例: 30分〜1時間、WorkManagerで実装)でサーバーへハートビートを送信する
- ハートビートには以下を含める: 端末ID / 送信時刻 / NotificationListenerServiceの有効状態 / ROLE_DIALER保持状態 / アプリバージョン / OS再起動からの経過

### 35.3 サーバー側の死活監視

- サーバーは各端末の最終ハートビート時刻を監視し、想定間隔を超えて途絶した場合、`device_health` イベント(WARNING〜CRITICAL)を生成して家族へ通知する
- 権限失効(NotificationListenerServiceの許可が外れた等)を含むハートビートを受信した場合も同様に通知する

### 35.4 限界事項

アプリが完全にアンインストールされた場合、端末側から能動的に通知することはできない(これは技術的に不可能)。この場合はサーバー側の「ハートビート途絶」検知が唯一の手がかりとなるため、35.3のタイムアウト検知が事実上の代替アンインストール検知として機能する。

## 36. インフラ構成(AWS) `[v2 新設]`

### 36.1 前提

個人・家族規模での運用(監視端末: 数台〜十数台、家族ユーザー: 数人〜十数人、イベント量: 端末あたり1日数十〜数百件)を前提とする。エンタープライズ規模のスケーラビリティは現時点では不要。

**結論: この規模であればAWSで月額$10〜20程度に収まる見込みのため、コストを理由に他バックエンドへ切り替える必要はない。** 具体構成は以下の通り。

### 36.2 推奨構成(Phase 1〜2)

| 用途 | サービス | 理由 |
|---|---|---|
| API + アプリサーバー | **Lightsail インスタンス**(1〜2GB RAM, ~$5〜10/月) | 固定料金で静的IP・一定のデータ転送量込み。ALBやNAT Gatewayを別立てするより個人規模では安い |
| PostgreSQL | 同一Lightsailインスタンス上にDockerで自前ホスト | RDS($15/月〜)やLightsail管理DB($15/月〜)を使わず、まずはコストを抑える。バックアップは`pg_dump`をcronで夜間S3送信 |
| 家族ユーザー認証 | **Amazon Cognito User Pool** | 無料枠(月間10,000 MAU)の範囲内で完全に収まる規模。MFAも標準対応 |
| 監視端末認証 | ペアリング時発行のAPIキー + 8.1の非対称鍵署名 | Cognitoは人間ユーザー向けのため、端末はシンプルな自前方式が適切 |
| Push配信 | Firebase Cloud Messaging(AWS外) | AWS側の課金は発生しない |
| 録音データ保存(Phase 3) | **S3**(SSE-KMSで暗号化) | 低頻度アクセスかつ低容量であれば数十円/月程度 |
| ログ・監査 | 監査ログ本体はPostgreSQL(audit_logsテーブル)、インフラログはCloudWatch Logs無料枠 | 家族画面での「誰が何をしたか」表示はPostgreSQLへの通常クエリで十分 |
| ドメイン・TLS | 独自ドメイン(年額) + Let's Encrypt(無料) | Route 53は必須ではない(お名前.com等の既存ドメインでも可) |

### 36.3 コスト試算(月額目安)

- Lightsailインスタンス: 約$5〜10
- Cognito: $0(無料枠内)
- S3(Phase 3導入後): 数十円〜$1程度
- **合計: 概ね$10〜15/月(約1,500〜2,300円/月)**

将来、監視端末・家族ユーザーが大幅に増える、あるいは複数家族向けSaaS化する場合は、以下へ段階的に移行する:

- Lightsail自前Postgres → **RDS PostgreSQL**(マネージドバックアップ・自動フェイルオーバー)
- Lightsailインスタンス → **ECS Fargate + ALB**(可用性・スケーラビリティ重視)

### 36.4 検討して不採用とした選択肢

- **API Gateway + Lambda + Aurora Serverless v2**: リクエスト課金は魅力的だが、Aurora Serverless v2は最小容量(0.5 ACU)でも待機コストが月$40程度発生し、この規模の常時稼働ワークロードには本構成より高くつく。将来的にトラフィックが非常に少ない・波がある場合は再検討の余地あり。
- **完全サーバーレス構成全般**: 個人規模かつ常時いくらかのトラフィック(ハートビート等)がある本システムでは、固定費の小さいLightsail/EC2の方が総コストで有利。

### 36.5 コストが問題化した場合の代替案(参考)

現時点の試算では不要と考えるが、参考として: Supabase(Postgres+Auth+Realtimeがバンドルされ、無料枠が広い)、Fly.io/Railway(小規模アプリのデプロイが簡単)、さくらのVPS/ConoHa(国内の固定額VPS)。AWSに慣れているというアドバンテージを活かせる本構成の方が、運用の学習コストは低いと考えられる。
